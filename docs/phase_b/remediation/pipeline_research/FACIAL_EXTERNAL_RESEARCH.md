**Viseme packs:** MPFB additionally offers **visemes01** (Microsoft-style viseme set) and **visemes02** (15-shape Meta/ARKit naming convention, e.g. `viseme_aa`, `viseme_CH`, `viseme_sil`). Only visemes02 is wired directly into the third-party "Lip Sync" Blender addon (by iocgpoly); all three packs (faceunits01, visemes01, visemes02) can be loaded on the same character simultaneously since they're just named shape keys. **Proxy propagation (eyelashes/eyebrows/teeth):** Confirmed that MPFB2 equips eyes, eyebrows, eyelashes, and teeth as separate mesh objects/proxies, and that the Rigify conversion path explicitly handles teeth deform bones and eyebrow/eyelash weighting as part of the face-rig conversion — i.e., face units are expected to work with proxy meshes, though the eyebrow/forehead weight interaction is a known rough edge requiring manual weight cleanup. **Partially verified** — could not find an explicit statement that ARKit face-unit *shape keys themselves* (as opposed to bone-driven Rigify controls) auto-propagate to proxy objects; this likely requires per-proxy shape-key duplication, standard for any MakeHuman-style modular character system. Flag as **UNVERIFIED (assume manual step required)** pending hands-on test in the actual Blender file.

## B. Apple ARKit 52-blendshape convention as a facial standard

ARKit's `ARFaceAnchor.BlendShapeLocation` defines **52 named facial-expression coefficients** (e.g. `jawOpen`, `mouthSmileLeft`, `eyeBlinkRight`, `browInnerUp`, `cheekPuff`, `tongueOut`). Separately, ARKit's face-tracking frame also reports **3 head-rotation and 6 eye-rotation values**, sometimes leading to the "61 values" figure quoted in some docs — but the blendshape *standard* itself is 52 channels. [ARKit Blendshapes reference](https://arkit-face-blendshapes.com/), [miniface.org guide](https://miniface.org/)

**Adoption as a de-facto industry standard:** Confirmed adopted (as an output/input target) by:
- NVIDIA Audio2Face-3D (outputs ARKit blendshape weights) — see section C
- Reallusion Character Creator / iClone ExPlus & HD facial profiles (ARKit profile support) — see section E
- MetaHuman (baked ARKit blendshape export path exists as a workaround, though native rig is RigLogic/bone-driven) — see section F
- Rokoko Face Capture (captures directly to the 52 ARKit channels) — see section D
- Ready Player Me avatars — ship ARKit-compatible blend shapes plus Oculus/Meta viseme mapping — [RPM Apple ARKit docs](https://docs.readyplayer.me/ready-player-me/api-reference/avatars/morph-targets/apple-arkit)
- MakeHuman/MPFB2 (faceunits01) — see section A
- Blender: Faceit addon, Auto2Face community wrapper — see sections C, G

**Known gaps in the raw ARKit set** (consistent across sources): no explicit **tongue** channel beyond `tongueOut` (no tongue-roll/tongue-tip shapes — Reallusion's ExPlus profile patches this with **11 additional Tongue Morph sliders** on top of the 52 ARKit shapes, see section E); no **neck** channels at all; only two **cheek** channels (`cheekPuff`, `cheekSquintLeft/Right`) which most pipelines find insufficient for strong emotional reads and extend with custom corrective shapes (Reallusion's HD facial profile addresses this with 262 blendshapes + 128 corrective morphs). Common extension pattern industry-wide: keep the 52 ARKit names as the interchange contract, then layer proprietary corrective/neck/tongue shapes on top for in-house use only.

## Cross-cutting license/legal notes

- **GPL/AGPL Blender addons (MPFB2, MB-Lab, Faceit, Human Generator's code) do not encumber your generated game content** — this is Blender's own stated position and is consistent across all these tools. The separate concern is always the *bundled digital-asset license* (e.g., Human Generator's Digital Asset License, MakeHuman's CC0/CC-BY split), which is a distinct legal layer from the addon's code license and is the one that actually governs whether you can ship meshes/textures in your game.
- **The recurring "runtime-embed yes, loose-asset-resale no" pattern** appears across Reallusion, Human Generator, and (implicitly) most commercial character-asset ecosystems: baking a purchased/generated character into a compiled game build is essentially always fine; redistributing the source `.fbx`/`.blend`/texture files as an extractable, standalone asset pack is essentially always prohibited. Design the build pipeline (bake to glTF/GLB with embedded/packed textures, no loose source files in the shipped product) with this pattern in mind regardless of which tool is chosen.
- **NVIDIA Audio2Face-3D's 2025 open-sourcing is the most favorable and lowest-risk item researched**: MIT code + Open Model License weights + confirmed "no ownership of outputs" + a workflow (bake-then-ship) that avoids any NVIDIA runtime dependency in the shipped game. This is the strongest-value item found in this whole research pass, conditional on a small-batch quality pilot (see Production economics below) and on having a CUDA-capable NVIDIA GPU available during production (already true for this studio's hardware, per project memory: 5090/3090/6900XT machines).
- **MetaHuman's opening-up is real but the Godot integration cost is currently high** (no native blendshapes; requires a RigLogic bake workaround or a from-scratch OpenRigLogic/GDExtension project) — do not treat "MetaHuman is now license-free to use outside Unreal" as equivalent to "MetaHuman is now easy to use in Godot."
